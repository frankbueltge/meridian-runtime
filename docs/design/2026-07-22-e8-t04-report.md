depends on E8-T01/E8-T02/E8-T03 (all merged into `main`). Executed 2026-07-22 on branch

## Implementation summary

`mrr release create --database-url … --artifact-root … --crate-id … --disclosure internal|public
[--classification-file …] --output-dir … --approved-by … --approval-statement-file …
--approval-mode single_human|dual --policy-version … [--correlation-id …]` assembles a deterministic
bundle directory (`ro-crate/` via `ExportService.export`, `report.md`/`report.html` via
`ReportService.render` + `render_markdown`/`render_html`, `release-manifest.json`, and a verbatim
copy of the persisted record as `release-record.json`) and persists the new `ReleaseRecord` object
kind — revision 1, atomically with a `release.approved` domain event whose `actor` is the approving
human, never a service/CLI default. `mrr release verify --database-url … --release-id … [--artifact-root
… | --bundle-dir …]` rebuilds the content either fresh from the archive or from an existing on-disk
bundle directory and compares it to the stored record, so "immutable release" is a checkable
property, not merely an assertion — a single flipped byte anywhere is caught and named.

Every A4 approval input (`--approved-by`, `--approval-statement-file`, `--approval-mode`) has NO
default anywhere — argparse level (`default=None`, not `required=True`) so this module's own
explicit check reports a custom refusal naming MRR-FR-102 rather than argparse's generic usage
error; absence is always exit 3. `approval_mode == "dual"` is schema/contract-valid (the vocabulary
docs/spec/01_SYSTEM_SPEC.md section 5 offers) but SERVICE-refused — this practice implements only
`"single_human"` (derived_decisions (b)). No publishing connector exists or is built here (ADR-0011
decision 4) — external publication remains impossible by absence, not a guard; this packet only
builds the precedent gate a future connector would have to check.

Six pieces:

- **`schemas/release-record.schema.json` + `packages/contracts/mrr/contracts/release_record.py`**
  (new, thirtieth entity pair) — `ReleaseRecord` per ADR-0011 decision 1 exactly: `crate_id`,
  `disclosure` (`internal`|`public`), `bundle` (`files`: sorted `[{path, sha256}]` — enforced by a
  Pydantic `model_validator`, not itself expressible as a JSON Schema array-order constraint —
  `root_hash`), `approval` (`approved_by` — a dedicated `PersonUrn` Annotated type, pattern-enforced
  `^urn:mrr:person:...` at BOTH the schema and the Pydantic layer per R1's own literal wording;
  `approval_statement` non-empty; `approval_mode` — a NEW, deliberately separate two-value Literal,
  never `mrr.contracts.common.ApprovalMode`, which is a different three-value vocabulary for a
  different concept), `status` (`released`|`superseded`). Registered in the contracts package and
  the schema/contract roundtrip harness like every sibling (see "Deviation from allowed_paths"
  below for where this touched two files the packet's own `allowed_paths` omitted).
- **`packages/domain/mrr/domain/lifecycles.py`** — `RELEASE_RECORD_LIFECYCLE`, the single edge
  `released -> superseded`, added purely by extending the file's existing parametrized structures
  (mirrors every prior extension in that file's own history). This packet never drives the
  transition itself — every `ReleaseRecord` it creates is a fresh revision-1 `"released"` record;
  the edge exists for a future E8-T05.
- **`services/control_plane/mrr/services/release/`** (new package):
  - `manifest.py` — pure, framework-free `compute_bundle_manifest`/`compute_root_hash`: walks a
    directory, excludes `release-manifest.json`/`release-record.json` by relative path, hashes each
    remaining file, and computes `root_hash` over the sorted per-file `"<sha256>  <path>\n"` lines
    (ADR-0011 names the RULE — sha256 over sorted per-file hash lines — not the exact byte format;
    this module's own concrete choice, flagged for reviewer scrutiny).
  - `errors.py` — the typed refusals R2 names (`NonPersonApproverError`,
    `EmptyApprovalStatementError`, `DualApprovalNotSupportedError`, `ReleaseCrateKindError`,
    `BundleRootHashMismatchError`) plus `ReleaseRecordKindError` (verify) and
    `ReleaseBundleFinalizationError` (the one named inconsistent state — see below).
  - `service.py` — `ReleaseService.create`: checks (in cheapest-first order) `approved_by` is a
    person-segment URN via `mrr.domain.identity.URN_PATTERN` directly, `approval_statement` is
    non-blank, `approval_mode == "single_human"`, `crate_id` resolves to an `EvidenceCrate`
    (`EvidenceCrate.sealed` is schema-fixed `const: true`, so resolving to the right KIND is the
    only additional fact needed), and `bundle.root_hash` matches the value recomputed from
    `bundle.files` — THEN mints identity/content-hash and persists revision 1 + the
    `release.approved` event atomically, `actor == approved_by`, `created_by == approved_by`, no
    separate `actor` kwarg exists on this method at all (ADR-0011 decision 2's own point). No
    update/delete/transition method — immutability by omission. See that module's own docstring,
    "Deliberate deviation: create() takes RAW approval inputs, not a pre-built ReleaseRecord", for
    why this differs from the sibling create-only services.
  - `bundle.py` — `assemble_and_release`: the R3 orchestration, composing `ExportService.export` and
    `ReportService.render`/`render_markdown`/`render_html` by composition only (zero new closure,
    render, or redaction logic — reviewer_resolution (4)) in the fixed order assemble-content ->
    persist -> finalize, with the ONE named inconsistent state
    (`ReleaseBundleFinalizationError`) — see "Atomicity analysis" below.
  - `verify.py` — `verify_rebuild`/`verify_bundle_dir`: two independent ways to compare a stored
    record's `bundle.files`/`root_hash` against independently-derived bytes (a fresh archive rebuild,
    or an existing on-disk directory), returning a uniform `VerifyResult` with per-path
    `missing`/`extra`/`changed` diffs.
- **`services/control_plane/mrr/services/cli/release_main.py`** (new) — the thin CLI, `mrr release
  create`/`mrr release verify`, NFR-012-ordered, exit map 0/2/3 (see "Exit code map" below).
  `main.py` gained one additive registration (import + `register_release_subcommand` call +
  dispatch `elif`, mirroring the export/report precedent, which itself needs exactly those two
  lines per registration).

### Atomicity analysis (reviewer_resolution (5), stop_condition 1)

The fixed order is **assemble-content -> persist -> finalize**. Steps 1 (assemble) and 3 (finalize)
never touch the database and can each fail with nothing durable written anywhere (temp directory
removed, `--output-dir` untouched). Step 2 (`ReleaseService.create`) is the ONE transaction boundary
— either the `ReleaseRecord` revision and its `release.approved` event both land or neither does
(the existing `record_object_revision_with_event` guarantee), so step 2 itself can never leave a
partial record/event pair. The ONLY inconsistent state this function can produce is therefore **step
2 succeeds, then step 3 fails**: the record is durably persisted with no corresponding bundle
directory on disk anywhere (the temp directory is still removed in this case too — nothing partial
is ever visible, at `--output-dir` or at an orphaned temp path). `mrr.services.release.bundle`
raises `ReleaseBundleFinalizationError` for exactly this case, carrying `release_id`/`revision`;
`release_main.py` prints its message verbatim (it already names the exact inconsistent state and
the recovery command, `mrr release verify --release-id <id>`) and exits 3. No second inconsistent
state exists — confirmed, not discovered mid-implementation (stop_condition 1's own check): step 1
never writes to the database at all (`ExportService`/`ReportService` are both read-only), and step 2
is a single atomic transaction by construction.

### Exit code map

`mrr release create`: `0` success (JSON: `release_id`, `revision`, `crate_id`, `disclosure`,
`approval_mode`, `root_hash`, `file_count`, `output_dir`); `2` dependency unavailable
(`--approval-statement-file` unreadable, `--classification-file` missing/forbidden/unreadable/
invalid, `--artifact-root` missing/not-a-directory, database unreachable); `3` refused
(`--output-dir` pre-existing, checked first; `--approved-by`/`--approval-statement-file`/
`--approval-mode` absent, naming MRR-FR-102; any `DomainError`/`ValueError` from
`assemble_and_release`, including the one named inconsistent state).

`mrr release verify`: `0` match (JSON: `release_id`, `mode`, `root_hash`, `matched`); `2` dependency
unavailable (`--bundle-dir`/`--artifact-root` missing/not-a-directory for their respective mode,
`--classification-file` missing/forbidden/unreadable/invalid for a rebuild of a public record,
database unreachable); `3` `--release-id` unresolved/wrong-kind, or a MISMATCH naming every
differing path (`missing`/`extra`/`changed`).

## Two disclosed additions beyond R4's own (evidently abbreviated) flag list

R4's own text lists `mrr release create`'s flags without `--policy-version`/`--correlation-id`.
Every OTHER event-writing CLI in this codebase (`mrr verification record`) requires
`--policy-version` explicitly and accepts an optional `--correlation-id`; the two read-only CLIs
(`mrr report render`/`mrr export ro-crate`) have neither, because neither writes an event.
`ReleaseService.create` DOES write one (`release.approved`), so `release_main.py` adds both flags,
mirroring `verification_main`'s own precedent exactly. There is deliberately NO `--actor` flag:
ADR-0011 decision 2 is explicit that the event's actor IS `approved_by`.

Similarly, `mrr release verify`'s rebuild mode adds `--classification-file` (required only when the
resolved record's own `disclosure` is `"public"`; forbidden with `--bundle-dir`, which never
re-renders anything) — mirroring `mrr report render`'s own identical rule. Without it, rebuilding a
public release's bundle would re-render a DIFFERENTLY-redacted report (no attestation supplied) and
spuriously mismatch even though nothing about the archive or the release actually changed.

Both are flagged prominently here, in the module docstrings, and are necessary — omitting either
would either make `ReleaseService.create` unusable through the CLI at all (no governance-act
`policy_version`), or make every public-disclosure rebuild-mode verify spuriously fail.

task-packets/E8-T04.yaml's `allowed_paths` lists `schemas/release-record.schema.json` and
`packages/contracts/mrr/contracts/release_record.py`, but — unlike every sibling packet that added
an entity (e.g. K1-T01.yaml lists `examples/*.example.json` for all six of its own entities;

EXISTING test, not one this packet added) fails hard the instant a new schema exists without a
matching example and `ENTITY_MODELS` entry — there is no way to satisfy R1 and keep `make
test-contract` green without touching both files.

This is treated as a packet drafting omission, not a deliberate scope restriction (per
stop_condition 2's own "the harness's conventions outrank this packet's convenience"), and BOTH
files were touched: `examples/release-record.example.json` (a new, illustrative fixture, matching
every sibling's own shape) and `scripts/check_contracts.py` (one import line + one `ENTITY_MODELS`
dict entry — the exact same two-line addition every prior entity-adding packet made in that file).
Flagged here, in `scripts/check_contracts.py`'s own updated module docstring, and repeated in this
report's own summary below — a disclosed blocking-dependency resolution per AGENTS.md rule 13, not
a silent workaround.

## Security / privacy implications

None new beyond E8-T01/T02/T03's own already-disclosed stance — the release path composes those
already-audited services and adds no new I/O surface beyond writing the bundle directory and one
database transaction. The A4 approval act itself is the new surface this packet specifically hardens:
`--approved-by`/`--approval-statement-file`/`--approval-mode` have no default anywhere (argparse,
service, or contract layer), so a script that forgets to supply them fails loudly (exit 3, naming
MRR-FR-102) rather than silently approving with a placeholder identity. `approved_by` is checked to
be a person-segment URN at THREE independent layers (JSON Schema pattern, Pydantic `PersonUrn`
Annotated type, and `ReleaseService.create`'s own explicit `URN_PATTERN` check against the raw
string) specifically so an agent-role, node, or practice identity can never stand in for the human
(MRR-FR-110). `root_hash` is recomputed, never trusted from input, at both boundaries that read one
(`ReleaseService.create` and both verify modes) — a caller cannot forge a manifest and have it
accepted. No credential, secret, or private key is read or written by this packet's own code; the
Ed25519 signing keys used in this report's own fixture capture are ephemeral, generated per test run,
exactly as E8-T01/T02's own fixtures already do. No publishing connector exists — external
publication remains impossible in this codebase by absence (ADR-0011 decision 4), not by a guard this
packet could accidentally weaken.

## Known limitations

- **No real release was created against the real archive** (reviewer_resolution (1),
  derived_decisions (a)): every `ReleaseRecord` this packet's own tests and this report's own capture
  create uses a synthetic person URN approver in a throwaway PostgreSQL schema. The owner's own first
  real release, if ever, is a separate, explicitly owner-driven act — nothing here schedules or
  suggests it.
- **The exact `root_hash` byte format (the "sorted per-file hash lines") is this module's own
  concrete choice**, not pinned by the ADR's own text — see `mrr.services.release.manifest`'s own
  module docstring for the full disclosure and rationale (a `sha256sum`-style two-space-separated
  checksums-line format, hashed via `mrr.crypto.hashing.content_hash`, never
  `mrr.crypto.canonical.canonicalize`, since there is no JSON object here to canonicalize).
- **`mrr release verify`'s rebuild mode of a `"public"` disclosure record requires re-supplying the
  SAME `--classification-file` attestation** the original release used (see "Two disclosed additions"
  above) — there is no mechanism to recover a forgotten attestation from the archive itself; a
  rebuild attempted without it is a dependency failure (exit 2), not a silent internal fallback.
- **`ReleaseService.create`'s own person-URN/statement/mode checks are intentionally redundant with
  the Pydantic contract layer** for the normal `ReleaseRecord.model_validate()` construction path (a
  malformed `approved_by` would already fail there) — the service-level checks exist as the layer a
  caller cannot route around even when constructing a record via `model_construct()` or receiving one
  from an untrusted source; `tests/unit/services/release/test_service.py` exercises them directly
  against the raw string inputs `create()` actually takes, not merely as dead code behind an
  already-validated object.
