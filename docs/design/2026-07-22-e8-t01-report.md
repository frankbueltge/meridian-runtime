**Task identifier:** task-packets/E8-T01.yaml (MRR-FR-055, first half). First task of Epic

## Implementation summary

`mrr export ro-crate --database-url … --artifact-root … --crate-id … --output-dir …`
materializes a self-contained, offline-verifiable directory from one sealed
`EvidenceCrate`: `ro-crate-metadata.json` (RO-Crate 1.1, hand-authored JSON-LD, no new
dependency), one RFC 8785 canonical JSON file per included MRR object, and the raw
artifact bytes under their content hashes.

Three pieces, mirroring the E3-T07 (`ProjectionService`) precedent throughout:

- **`packages/domain/mrr/domain/ro_crate.py`** — pure, I/O-free functions building (a)
  the deterministic export plan (fixed, collision-free file naming:
  `objects/<urn ':'→'_'>.json`, `artifacts/<64-hex>`, `ro-crate-metadata.json` at the
  root) and (b) the RO-Crate metadata document as a plain dict: `@context` (the RO-Crate
  1.1 context plus one `mrr:` extension prefix), a metadata file descriptor, a root data
  entity (`hasPart` naming every file, `datePublished` always the crate's own stored
  `created_at` — never wall-clock), one `File` entity per exported file
  (`contentSize`/`mrr:contentHash`, plus an `about` link back to its contextual entity —
  a disclosed addition beyond R1's literal minimum, documented in the module docstring),
  and one contextual entity per MRR object (`mrr:urn`/`kind`/`contentHash`/`practiceId`,
  and `mrr:signature` verbatim whenever the stored body actually carries one — which, in
  this packet's own closure, is only ever the crate). No `prov:*` term anywhere
  (E8-T02's boundary), asserted by a scanning unit test.
- **`services/control_plane/mrr/services/export/service.py`** — `ExportService`,
  read-only (`ObjectRepository`/`EdgeRepository`/the narrow event-journal
  Protocol/`ArtifactStore`; no `RecordRevisionWithEvent`/`RecordEdgeWithEvent` anywhere).
  Resolves the R2 closure — the crate, its `source_records`/`evidence_anchors`/
  `proposed_claims` arrays (fail-fast, naming the first unresolvable urn), the provenance
  BFS from each proposed claim, and every `VerificationResult` the event journal shows
  recorded against an included claim — fetches every artifact's bytes (collecting **all**
  missing hashes before failing, never first-miss-wins), and writes the directory
  atomically (temp sibling directory, `os.replace` onto the target as the last act; a
  pre-existing target, file or non-empty directory, refuses before any work).
- **`services/control_plane/mrr/services/cli/export_main.py`** — the thin CLI, ordered
  per MRR-NFR-012 (`--output-dir` conflict, then `--artifact-root` readability, then
  database reachability, then exactly one `ExportService` call); exit codes `0`/`2`/`3`.
  `main.py` gained exactly one additive registration block, mirroring the
  verification/synthesis precedent.

### A specification-text imprecision worth flagging (not a stop condition)

The packet's own derivation text names `mrr.domain.projection.build_provenance_map` as
the BFS to reuse. That function does not live there: `mrr.domain.projection` (the pure
module) holds only the `ProvenanceEdge`/`ProvenanceMap` dataclasses and unrelated
claim-table shaping functions — the actual traversal (`build_provenance_map`,
`_trace_provenance`, `_outgoing_provenance_hops`) lives on the application-layer
`mrr.services.projection.service.ProjectionService`, since a BFS over
`ObjectRepository`/`EdgeRepository` is inherently I/O, which the pure domain layer
cannot perform. This is a minor imprecision in the packet's own prose, not a
specification conflict and not the "modifying `mrr.domain.projection`" stop condition:
no modification was needed anywhere, and no divergent fork of the traversal logic was
written. `ExportService.export` satisfies the actual, intended requirement — R2(c)'s own
words, "reusing that module's traversal semantics, not re-inventing them" — by
COMPOSING an internal `ProjectionService` instance (built from the exact same
dependencies `ExportService` already holds) and calling its already-shipped,
already-tested `build_provenance_map` once per proposed claim. Documented in
`ExportService`'s own module docstring for reviewer scrutiny.

One genuine finding from writing these tests: this codebase's own established fixture
convention elsewhere (`"content_hash": "sha256:" + "a" * 64`, a placeholder never
recomputed) would make AT1's hash-recomputation check fail for a reason unrelated to the
code under test. This module's own fixtures therefore recompute a REAL content hash
(`mrr.domain.hashing_policy.compute_content_hash`) before persisting each `SourceRecord`/
`EvidenceAnchor`/`Claim`/`VerificationResult` — the crate itself already gets a real hash
from `EvidenceCrateSealer.seal` unconditionally.

## Security / privacy implications

None new. The export path is read-only against already-sealed, already-persisted state;
no credential, secret, or private key is read or written by `ExportService`/
`export_main.py` (an Ed25519 signature VALUE — already public inside the sealed crate —
is copied verbatim, never a private key). A local directory export is explicitly NOT
publication (derived_decision (d)): nothing in this packet contacts anything external,
and the A4 publication-approval gate (E8-T04) is not implicated. Classification/
disclosure filtering of exported object bodies is out of this packet's scope — R2's
closure is defined purely structurally (crate arrays + provenance + verifications), with
no redaction step; a future packet integrating export with `mrr.domain
.public_correction_view`'s fail-closed redaction (or an equivalent) would be needed
before this command is safe to run against a crate carrying non-`PUBLIC` classified
objects and hand the result to an external party. Flagged as a known limitation below,
not silently assumed safe.

## Known limitations

- **No classification/redaction gate.** `ExportService.export` exports every object in
  the R2 closure regardless of its `classification` field. This packet's own scope
  (derived_decision (d)) is explicitly "a local directory export is NOT publication" —
  redaction/attestation is out of scope here, but a caller who runs this command against
  a crate whose closure includes `RESTRICTED`/`SENSITIVE`/`PARTICIPANT_IDENTIFIABLE`
  objects gets them exported in full. Worth an explicit decision before E8-T04
  (publication) builds on top of this export path.
- **Referenced-urn resolution is fail-fast, not aggregated.** Unlike the artifact-bytes
  check (R3's own explicit "check all, report all" requirement), an unresolvable
  `source_records`/`evidence_anchors`/`proposed_claims` entry raises immediately, naming
  only that one urn — R2's own text ("naming the URN", singular) supports this reading,
  but a caller debugging multiple simultaneously-broken references sees them one at a
  time, re-running after each fix.
- **`contentSize` is a plain JSON number**, not a `schema.org`-typed string — a
  disclosed, judgment-call choice (documented in `mrr.domain.ro_crate`'s module
  docstring) since the packet does not specify a representation and an exact byte count
  is more useful/unambiguous than an informal size string.
- **`os.replace` on a directory target relies on POSIX semantics**, confirmed directly
  against this project's macOS/Linux runtime targets (an existing EMPTY directory is
  atomically replaced; a non-empty directory or file raises `OSError`, a second,
  defense-in-depth check behind the up-front `output_path_conflict` refusal). Windows
  directory-rename semantics were not verified and are out of this task's runtime scope.

## Specification conflicts / notes for reviewer scrutiny

1. **Derivation-text imprecision, not a conflict** — see "A specification-text
   imprecision worth flagging" above: the packet's own derivation text names
   `mrr.domain.projection.build_provenance_map`, which does not exist; the actual BFS
   lives on `mrr.services.projection.service.ProjectionService`. Resolved by composing
   `ProjectionService` internally rather than forking its traversal — no stop condition
   triggered, since no modification to `mrr.domain.projection` was ever needed.
2. **The extension-vocabulary URI is a disclosed placeholder** — `MRR_VOCAB_URI =
   "https://example.invalid/mrr/vocab#"`, reusing the exact authority every
   `schemas/*.schema.json` `$id` already uses, per the packet's own `specification_gaps`
   entry ("until the owner's site-coupling decision lands a real host"). Not guessed as
   if settled — flagged again here, at the point of use.
3. **No RO-Crate-version conflict encountered.** RO-Crate 1.1's root data entity
   requires `datePublished` (MUST, ISO 8601, minimum day precision) — the crate's own
   `created_at` already satisfies this without any invented value, so the packet's own
   stop condition ("a mandatory wall-clock date the archive cannot truthfully supply")
   was never triggered.
4. **The "about" link on object File entities** (tying an exported file back to its own
   contextual entity) is a disclosed addition beyond R1's literal minimum enumeration —
   see `mrr.domain.ro_crate`'s module docstring for the full rationale (costs nothing,
   fully derivable from the already-documented naming convention, serves the packet's own
   "inspect ... without the running MRR database" objective).
