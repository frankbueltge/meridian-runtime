# E8-T05 packet report — correction banner and release supersession (E8 close-out)

**Task identifier:** task-packets/E8-T05.yaml (docs/spec/adr/ADR-0011-RELEASE-RECORD-AND-A4-APPROVAL-EVENT.md,
`mrr.domain.lifecycles.RELEASE_RECORD_LIFECYCLE`'s own reserved `released -> superseded` edge). Fifth and
closing task of Epic E8, depends on E8-T04 (merged into `main`). Executed 2026-07-22 on branch
`e8-t05-banner-supersession`, cut from `origin/main` at `69f2abb` (the packet's own governance/approval commit).

## Implementation summary

Three pieces, composed additively over E8-T04's already-shipped machinery, with zero forbidden-path edits:

1. **`mrr.domain.release_status`** (new, pure): `compute_release_banner(release_body, correction_bodies,
   duplicate_unsuperseded_releases)` computes the three-verdict banner — `superseded` (release's own
   `status`, naming `labels.superseded_by`), else `corrections_affect_this_release` (any correction whose
   `affected_objects`/`impact_objects` intersect the release's own EXPORTED object set — derived by
   `exported_object_urns`, which inverts `mrr.domain.ro_crate.object_relative_path`'s naming rule against
   the release's own `bundle.files[].path` entries under `ro-crate/objects/` — AND whose `created_at` is
   strictly later than the release's own `created_at`, both parsed as real `datetime` values, never
   wall-clock-read), else `current`. The `duplicate_unsuperseded_releases` anomaly flag rides alongside
   every verdict, supplied by the caller (this module has no repository access to compute it itself).
2. **`ReleaseService.supersede`/`.status`** (extending E8-T04's `mrr.services.release.service.ReleaseService`):
   `supersede(release_id, *, superseded_by, approved_by, policy_version, correlation_id)` writes the OLD
   record's own next revision — `status` -> `"superseded"`, `labels["superseded_by"]` set, `approval`/
   `bundle` carried forward byte-identical — atomically with one `release.superseded` event whose `actor`
   is `approved_by`, driven through `mrr.domain.lifecycles.RELEASE_RECORD_LIFECYCLE.assert_transition`
   (the state machine ADR-0011 reserved this edge on). Five typed refusals: `NonPersonApproverError`
   (reused from `create`), `SelfSupersessionError`, `ReleaseRecordKindError` (reused), `AlreadySupersededError`,
   `SupersedingReleaseNotReleasedError`. `status(release_id)` is the read-only companion: resolves the record,
   discovers every `CorrectionEvent` this practice has ever recorded (a small, disclosed duplication of
   `ProjectionService`'s own genesis-event-scan pattern — composing `ProjectionService` itself would need
   an `EdgeRepository` this service has no other use for), scans for sibling `ReleaseRecord`s sharing the
   same `crate_id` (the duplicate-unsuperseded anomaly), and calls `compute_release_banner`. `event_log` is
   a new, OPTIONAL keyword-only constructor parameter (`None` by default) so E8-T04's own two existing call
   sites (`mrr.services.release.bundle.assemble_and_release`, `tests/unit/services/release/test_service.py`)
   stay byte-identical.
3. **`mrr.domain.research_report`** gains an OPTIONAL `release_banner: ReleaseBannerInput | None = None`
   input on `build_report` (threaded onto a new `ResearchReport.release_banner: ReleaseBannerSection | None`
   field, defaulting to `None`). Absent (every existing call site) → `None` all the way through, zero new
   rendered bytes (AT3's own regression, proven structurally: both renderers gate the ENTIRE block behind
   one `if model.release_banner is not None` check, before section 1, and never touch any other section's
   bytes). Present → both renderers emit a "Release status" block FIRST, before "## 1. Header"/`<h2>1.
   Header</h2>`, carrying the verdict/release urn/`superseded_by`/anomaly flag verbatim (never gated — none
   of those fields is ever passed through `_redact`/`build_public_correction_row`) plus one line per
   affecting correction, whose own `reason`/`requested_action` free text IS gated — through the SAME,
   already-tested `mrr.domain.public_correction_view.build_public_correction_row` this module already calls
   for the Claim-assertion case, never a third, competing redaction formula. `ReportService.render` gains
   the optional `release_id: Urn | None = None` parameter (R3's own words: "computes the banner via R2") —
   resolves the banner via an internally-held `ReleaseService` (constructed with a never-invoked
   `RecordRevisionWithEvent`, mirroring this exact class's own `_NeverInvokedArtifactStore` precedent one
   section up) and the raw `CorrectionEvent` body of every affecting correction, handing both into
   `ReleaseBannerInput` for `research_report.py` to redact and shape.
4. **CLI** — `mrr release supersede` (the full `create` flag set, factored into a new, reused
   `_add_create_flags` helper, PLUS `--supersedes <release-urn>`) and `mrr release status --database-url
   --release-id`, registered additively on the EXISTING "release" subparser tree; `main.py` untouched (its
   existing `register_release_subcommand` call and generic `release_main.run_command(args)` dispatch already
   cover both new subcommands — R4's own fallback line was checked and confirmed NOT required). Neither new
   subcommand imports `mrr.services.release.service`/`mrr.domain.release_status` directly — both reach that
   layer exclusively through two new composition functions in `mrr.services.release.supersede`
   (`create_and_supersede`/`resolve_release_status`), extending E8-T04's own "no domain behavior in the CLI"
   law (`tests/unit/architecture/test_release_cli_boundary.py`, left byte-for-byte unmodified — its own
   forbidden-import list already excluded `mrr.services.release.service`, so nothing there needed to change).

### The two-transaction supersede flow and its one named inconsistent state

`create_and_supersede` runs the fixed order reviewer_resolution (2) names: (1) `assemble_and_release` — the
UNCHANGED E8-T04 function, producing the NEW release exactly as `mrr release create` does; (2)
`ReleaseService.supersede` on `--supersedes` (the OLD release), naming the new release's own freshly-minted
id. Step 1 is already independently atomic (E8-T04's own "Atomicity analysis"); step 2 is a single atomic
database transaction by construction (one revision write plus one event, the same
`record_object_revision_with_event` primitive `create` itself uses). The ONLY inconsistent state this
composition can therefore produce is **step 1 succeeds, step 2 fails**: a fully valid, independently-approved
NEW release exists with no corresponding supersession of the old one —
`mrr.services.release.errors.SupersessionIntermediateStateError`, printed verbatim by `release_main.py`,
names both release ids and points at `mrr release status` (the `duplicate_unsuperseded_releases` anomaly)
for detection. No second inconsistent state exists (stop_condition (2) checked, not triggered — see
"Specification conflicts" below).

### Exit code map (new commands only — `create`/`verify` unchanged from E8-T04)

`mrr release supersede`: `0` success (JSON: `create`'s own eight fields PLUS `supersedes`/
`supersedes_revision`/`supersedes_status` — the OLD release's own id, its new revision number, and
`"superseded"`); `2` any of `create`'s own dependency failures (identical checks, identical messages,
`supersede`-prefixed); `3` any create-side refusal, OR `SupersessionIntermediateStateError` (the one named
inconsistent state, printed verbatim).

`mrr release status`: `0` for **every** successfully computed verdict, including `superseded` and
`corrections_affect_this_release` (derived_decisions (c): "a superseded release answering 'superseded' is
the system working, not failing" — scripts branch on the JSON `verdict` field, never the exit code, for this
one command). Prints one JSON line: `verdict`, `release_id`, `crate_id`, plus `superseded_by` (only when
applicable), `affecting_corrections` (only when non-empty, each entry `{"correction_id", "intersecting_
object_ids"}`), and `anomaly` (only when `duplicate_unsuperseded_releases` is true — the literal string
`"duplicate_unsuperseded_releases"`, not a bare boolean, so a future second anomaly kind would not need to
change this field's own shape). `2` database unreachable. `3` `--release-id` unresolved or wrong-kind.

## Security / privacy implications

None new beyond E8-T04's own already-disclosed stance. `supersede`'s own A4 approval inputs
(`--approved-by`/`--approval-statement-file`/`--approval-mode`) have NO default anywhere, identically to
`create` — the SAME three flags, the SAME argparse `default=None` discipline, the SAME custom MRR-FR-102
refusal message (prefixed `supersede` instead of `create`). `approved_by` is checked to be a person-segment
URN at the SAME layer `create` already checks it (`ReleaseService`'s own `URN_PATTERN` match, independent of
the Pydantic `PersonUrn` type). The banner's own free-text redaction reuses
`mrr.domain.public_correction_view.build_public_correction_row` — the SAME already-audited fail-closed
formula every other correction free-text field in this codebase already goes through; no new redaction rule
was invented. `mrr release status` reads the archive only — no A4 input, no write path, no new attack
surface. No credential, secret, or private key is read or written by this packet's own code. No real release
or supersession was performed against the real archive — every `ReleaseRecord` this packet's tests and its
own capture create/supersede uses a synthetic person URN approver in a throwaway PostgreSQL schema
(derived_decisions (d)).

  mirroring `ProjectionService`'s own established "no `list_by_kind` repository method exists" limitation
  (task-packets/E3-T07.yaml's own documented rationale) — this does not scale to an unbounded event log any
  better than `ProjectionService`'s own two builders already do; a future indexed "list by kind" repository
  method would let this be a targeted query instead, out of this packet's own scope.
- **The banner's `corrections_affect_this_release` population and section 5's unresolved-critical-correction
  population are deliberately DIFFERENT sets** (no severity/status filter on the banner's own intersection
  test, per R2's own literal text) — a report rendered with a release context can legitimately show a
  correction in one section and not the other, or vice versa; this is R2's own design, documented in both
  `mrr.domain.release_status`'s and `mrr.domain.research_report`'s own module docstrings, not a rendering
  inconsistency.
- **`ReportService.render`'s new `release_id` parameter performs no cross-check** that the named release is
  actually rooted on the crate being rendered — a caller supplying a mismatched pair gets a banner from an
  unrelated release's own context, silently. This mirrors this class's own existing "pure composition, no
  invented cross-checks" stance elsewhere (e.g. it does not verify `crate_id` against anything beyond what
  `resolve_closure` itself already checks) and is disclosed here for reviewer scrutiny rather than silently
  assumed safe.
- **`_run_supersede_command` is a disclosed, deliberate near-duplicate of `_run_create_command`**, not a
  shared-helper refactor of the run-command bodies (only the flag-DECLARING code, `_add_create_flags`, is
  actually shared) — a deep behavioral refactor risked an unintended change to `_run_create_command`'s own
  already-tested, byte-for-byte-preserved code path; the near-duplicate keeps that path completely untouched.
