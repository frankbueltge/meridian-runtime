**Task identifier:** task-packets/E8-T02.yaml (MRR-FR-055, second half). Second task of

## Implementation summary

The same `mrr export ro-crate` invocation now additionally expresses the W3C PROV view
of the exported closure, INSIDE the same `ro-crate-metadata.json` document (no second
file, no named graphs — one document a third party reads): a second `@context` prefix
(`prov` → `http://www.w3.org/ns/prov#`), PROV types on every contextual entity and every
artifact `File` entity, the four spec-named relations wherever the archive actually
holds the underlying fact, and minimal stub contextual entities for any prov-referenced
urn the closure never resolved. The exported FILE SET (`objects/*.json`, `artifacts/*`)
does not change at all — only `ro-crate-metadata.json` grows.

Three pieces:

- **`packages/domain/mrr/domain/prov_mapping.py`** (new, pure, no I/O, no repository
  types) — the kind→PROV-type table (docs/spec/02_DOMAIN_MODEL.md section 6's ten rows,
  transcribed verbatim, plus the packet's three derived rows: `EvidenceCrate`/
  `EvidenceAnchor` → `prov:Entity`, `VerificationResult` → `prov:Activity`); the
  urn-entity-segment→PROV-type fallback for R3 stubs (nine rows, exhaustive); five
  relation-deriving functions implementing R2(a)–(e) exactly (`derived_from` typed edges
  → `prov:wasDerivedFrom`; `RunManifest.executor_id`/`parameters` →
  `prov:wasAssociatedWith`/`prov:used`; `VerificationResult.reviewer_id`/`target_id`+
  `evidence_inspected` → `prov:wasAssociatedWith`/`prov:used`; `EvidenceCrate.run_id` →
  `prov:wasGeneratedBy`, reused for every artifact `File` entity too); and
  `relation_target_urns`, the one generic extractor `mrr.domain.ro_crate` uses to know
  which referenced urns need an R3 stub.
- **`packages/domain/mrr/domain/ro_crate.py`** (extended) — `build_ro_crate_metadata`/
  `build_export` gain a new `provenance_edges: Sequence[ProvenanceEdge] = ()` parameter;
  the builder now emits the `prov` context prefix, a two-element `[mrr:<kind>,
  prov:<Type>]` `@type` list wherever a kind mapping exists (a bare `mrr:<kind>` string
  otherwise — the packet's own required "pick ONE deterministic representation"), every
  R2 relation property, `prov:wasGeneratedBy` on artifact `File` entities, and sorted,
  deduplicated R3 stub entities appended after the real contextual entities. `hasPart`
  and every object/artifact file's own bytes are untouched — the file-set regression
  invariant holds by construction (`provenance_edges` never reaches
  `build_export_plan`).
- **`services/control_plane/mrr/services/export/service.py`** (R4 wiring) —
  `ExportService.export` now accumulates every `ProvenanceMap.edges` hop from every
  proposed claim into a `set[ProvenanceEdge]` (frozen/hashable, so the set itself IS the
  "deduplicated union" R4 asks for), sorts it by `(source_id, relation, target_id, via)`
  — the same key `ProjectionService._trace_provenance` already sorts one claim's own
  hops by — and passes the result to `build_export` instead of discarding it. No new
  repository/store call, no closure change, no CLI change.

## Security / privacy implications

None new beyond E8-T01's own already-disclosed stance (export is read-only; no
credential/secret/private key touched). The PROV layer adds no new field a consumer
could not already read from the exported object bodies themselves — `prov:` relations
restate, in a standard vocabulary, exactly the urns already sitting in
`executor_id`/`reviewer_id`/`target_id`/`evidence_inspected`/`run_id`/typed
`derived_from` edges. R3 stub entities carry a bare urn and (sometimes) a PROV type —
never a name, a role beyond "reviewer/executor", or any other attribute — so they add no
new disclosure surface for `PARTICIPANT_IDENTIFIABLE`/`SENSITIVE` data beyond what the
export already does (E8-T01's own known limitation, "no classification/redaction gate",
carries over unchanged: this packet does not add one either).

## Known limitations

- **The "executor" urn-segment gap** (flagged prominently in `mrr.domain.prov_mapping`'s
  own docstring, in `mrr.domain.ro_crate`'s `_stub_entity`, and in the integration test
  itself): this codebase consistently mints `RunManifest.executor_id` with urn entity
  segment `"executor"`, but task-packets/E8-T02.yaml R1's own fallback table names only
  six segments (`person`/`agent-role`/`practice`/`node`/`run`/`artifact`/`source-record`/
  `claim`/`evidence-anchor` — nine, `executor` not among them). An unreached run's own
  executor stub therefore carries `@id`/`mrr:urn` but NO `@type` — not a bug, the
  packet's own literal "every other segment → None" rule applied faithfully, but a real
  gap for a future packet (or an ADR) to close if `prov:Agent` is the intended reading.
- **`RunManifest.parameters` artifact-urn scan is a disclosed judgment call**, not a
  spec-given field name: `parameters` mirrors `TaskBundle.instructions`, a genuinely
  open `{"type": "object"}`. This module reads "every artifact URN its parameters name"
  as a recursive scan for strings matching the artifact urn pattern anywhere inside that
  object — documented at the point of use (`mrr.domain.prov_mapping`'s own docstring,
  "(b)" bullet), not silently assumed.
- **No classification/redaction gate** — carried over unchanged from E8-T01; still out
  of scope here.
- **`Review`/`CorrectionEvent` mapping rows are untested against a real closure** —
  transcribed per derived_decisions (b) since no closure this exporter can build reaches
  either kind yet; a future packet inherits the row rather than re-deriving it.

## Specification conflicts / notes for reviewer scrutiny

1. **The "executor" gap** (see "Known limitations" above) is the one genuine
   specification gap this packet's own implementation surfaced — not a stop_condition
   (it is a URN-SEGMENT fallback gap for an R3 STUB, not an unrecognized CLOSURE KIND
   the spec table or derived_decisions (a) fails to name), but flagged per the packet's
   own instruction to record gaps rather than guess.
2. **No stop_condition was triggered.** Every closure kind this packet's own extended
   integration fixture produces (`EvidenceCrate`, `SourceRecord`, `EvidenceAnchor`,
   `Claim`, `VerificationResult`, `RunManifest`) is named by either the spec table or
   derived_decisions (a); the exported file SET is unchanged (proven by construction in
   `test_provenance_edges_do_not_affect_the_export_plan`, not merely asserted).
3. **AT2's own closure-identity test needed a filter fix**, not a design change: R3
   stubs now also carry `mrr:urn` (so the PROV graph can name them), which would have
   made E8-T01's own `"mrr:urn" in entity` filter over-count the R2 closure the moment
   any stub existed. Switched to `"mrr:kind" in entity` — the one field only a REAL,
   resolved contextual entity ever carries — a mechanical fix, not a reinterpretation of
   what "the R2 closure" means.
4. **The `@type` list order (`mrr:` first, `prov:` second) and the relation-value
   cardinality convention (single `{"@id": ...}` for `wasAssociatedWith`/
   `wasGeneratedBy`, always a list for `wasDerivedFrom`/`used`)** are disclosed,
   deterministic representation choices — task-packets/E8-T02.yaml itself asks for "ONE
   deterministic representation, documented" for the `@type` case; the relation-value
   convention is this module's own analogous choice for the same reason, documented in
   `mrr.domain.prov_mapping`'s own docstring.
